Performance

The benchmark executable measures JSON lookup performance across small files, larger inputs, controlled traversal cases, and an experimental memory-mapped large-file path.

View Results Benchmark Design

Benchmark Design

Performance experiments are implemented separately from the correctness tests in benchmark.cpp. The executable currently exposes four benchmark modes.

Mode Purpose Status
Single Query Compare lookup time between the small and larger booking datasets. Implemented
Many Queries Intended for repeated multi-query experiments. Not implemented yet
Big File Compare several traversal patterns through big.json. Implemented
Huge File Exercise the memory-mapped parsing path on a locally generated 1 GB JSON document. Experimental
Correctness testing and performance measurement are intentionally separate. GoogleTest verifies that results are correct, while the benchmark executable measures execution time.

Running the Benchmark

Configure and build the project: 

cmake -S . -B build
cmake --build build

Run the benchmark executable: 

./build/benchmark

The program then displays: 

Which test?
1 : Single Query
2 : Many Queries
3 : Big File
4 : Huge File
::

The implemented timing modes allow the experiment to be repeated multiple times so an average can be calculated.

Measured Results

The most current results come from two experiments: a 100-run input-size comparison and a 1,000-run controlled traversal benchmark.

Input-Size Comparison

The Single Query benchmark was repeated 100 times. The reported result is the average elapsed time for each file and lookup.

Dataset Lookup Average Time
~1 KB booking file Entry 0 → Booking_ID 0.0532 ms
~1 MB booking file Entry 1800 → Booking_ID 4.5208 ms 
average of 100 runs
1 KB, entry 0:      0.0531858 ms
1 MB, entry 1800:   4.52082 ms

The larger test takes substantially longer because it processes a much larger file and accesses an element farther into the JSON array.

This benchmark includes file opening, reading the document into a string, and JSON traversal. It therefore represents an end-to-end lookup rather than pure traversal time.

Interpreting the Results

Input Size Has a Visible Effect

The end-to-end booking benchmark increased from about 0.053 ms on the small input to about 4.52 ms on the larger input.

Traversal Is Lightweight on Small Fixtures

The controlled big.json queries complete in single-digit to low double-digit microseconds on this benchmark run.

Unicode Handling Remains Comparable

Raw UTF-8, escaped Unicode, surrogate-pair, and escaped quote lookups remain within the same general timing range.

Query Shape Matters

Object width, nesting, array navigation, escaping, and target position all change the amount and type of work performed by the traversal helpers.

Sequential Lookup Behavior

The engine does not construct a hash table or global index of all JSON keys. When seekComponent() searches an object, members are examined sequentially until the requested component is found or the object ends.

Therefore, the amount of JSON text that must be examined can depend on where a key appears within its container.

The current microbenchmark does not show a simple “first key is always faster than last key” relationship. At microsecond scale, caching, measurement overhead, branch behavior, and the exact fixture layout can affect individual measurements.

Large-File Optimization: Memory Mapping

The project also includes an alternative loading path for very large files: 

std::string_view json =
    json_parser::mapFile(path);

mapFile() uses a read-only memory mapping and exposes the mapped bytes through std::string_view.

String-Based Loading

std::ifstream file(...);

std::string json =
    json_parser::jsonToString(file);

The full document is copied into a new string before querying.

Mapped Loading

std::string_view json =
    json_parser::mapFile(path);

The parser views the mapped file directly without first copying the complete file into another large string.

This optimization is especially relevant for very large JSON files because the traversal functions already operate on std::string_view.

Memory mapping changes how the document is loaded and exposed to the parser. It does not replace the engine's sequential component-search algorithm.

Experimental 1 GB Benchmark

The benchmark program includes an experimental mode using a locally generated JSON file of approximately 1 GB: 

jsonFiles/data_1gb.json

The benchmark executes: 

DISPLAY {"logs" {"591518"}}

This mode is intended to evaluate querying a very large memory-mapped document without first creating a complete std::string copy.

Timing methodology under review: the latest 1 GB benchmark run produced an unrealistically high calculated throughput.

The memory-mapped execution path itself is implemented and can be exercised, but the timing boundaries for this benchmark should be corrected and re-run before using it for quantitative performance claims.

Performance Takeaways

Larger Inputs Cost More

The measured end-to-end lookup increased substantially between the small booking fixture and the approximately 1 MB fixture.

Traversal Can Be Isolated

Loading big.json before timing makes it possible to measure traversal separately from disk input.

Different Paths Exercise Different Work

Nesting, array lookup, Unicode conversion, escaped strings, and missing components all exercise different helper paths.

Memory Mapping Supports Large Inputs

The mapped-file path allows a large document to be exposed as a std::string_view without creating another full-size JSON string.
