Testing

The JSON Query Engine uses GoogleTest to verify query parsing, JSON traversal, FIND and DISPLAY behavior, Unicode handling, malformed inputs, file handling, and JSON edge cases.

Run the Tests View Coverage

Testing Overview

Automated tests are split between two primary test files:

tests/queryparsertest.cpp

Tests the conversion from raw query strings into ParsedQuery and JSONType structures.

24 expanded test cases

tests/jsonparsertest.cpp

Tests file behavior, path lookup, command execution, Unicode, literals, empty structures, and edge cases.

72 expanded test cases
The parameterized GoogleTest suites expand into multiple named test cases. Across both test files, the current source defines 96 individual cases.

Testing Framework

The project uses GoogleTest 1.17.0, downloaded automatically by CMake through FetchContent. 

FetchContent_Declare(
    googletest
    URL https://github.com/google/googletest/archive/refs/tags/v1.17.0.zip
)

The test executable is built as: 

JSONQL

CMake also enables test discovery with: 

gtest_discover_tests(JSONQL)

This allows the individual GoogleTest cases to be registered with CTest.

Running the Test Suite

From the project root, configure and build the project: 

cmake -S . -B build
cmake --build build

The tests can then be run directly with the GoogleTest executable: 

./build/JSONQL

They can also be run through CTest: 

cd build
ctest --output-on-failure
The build defines JSON_DATA_DIR as an absolute path to the repository's jsonFiles directory, so the tests do not depend on which working directory they are launched from.

Query Parser Tests

tests/queryparsertest.cpp verifies that raw query strings produce the expected recursive representation.

Valid Query Parsing

The largest parameterized parser suite tests 13 valid query structures.

Simple Queries

Verifies basic commands and field tokens. 

FIND {employees}

Multiple Fields

Checks that sibling token order is preserved. 

FIND {employees name}

Array Index Tokens

Confirms numeric positions remain string tokens in the parsed representation. 

FIND {employees 0 name}

Recursive Nesting

Verifies multiple nested brace levels produce nested JSONType vectors. 

FIND {a b {c d {e f {g h}}}}

Quoted Keys

Ensures spaces inside quoted keys remain part of the same key. 

FIND {"first name"}

Empty Keys

Confirms that "" remains a valid empty JSON key rather than being discarded. 

FIND {""}

Whitespace Handling

Tests verify both repeated spaces and leading/trailing spaces: 

FIND   {employees    name}

   FIND {employees name}

Extra whitespace should not create empty query tokens.

Empty Input

Two cases verify that empty and whitespace-only input leave the parsed result empty. 

""


"     "

Invalid Query Handling

Four malformed-query cases verify that the parser throws std::runtime_error instead of returning partial data.

  • Unmatched closing brace.
  • Closing brace immediately after the command.
  • Unknown command such as FETCH.
  • Unterminated quoted string.

Parser State

Additional standalone tests check state between consecutive queries.

Replace Previous Query

Parsing a second query must replace the previous result instead of appending to it.

Record Command

Verifies that FIND, DISPLAY, FILTER, and the parser's recognized command values are stored correctly.

FILTER Metadata

Checks that one FILTER argument is classified as regex and two arguments are classified as numeric range.

Reset FILTER State

Confirms regex metadata does not leak from one parsed query into the next.

Basic JSON Traversal Tests

The lower-level path-based parsejson(json, path) interface is tested against multiple fixture files.

Fixture Example Path Expected Result
employee.json employees → 0 → name "Laura"
employee.json employees → 2 → salary 95000
employee.json employees → 0 → skills → 1 "Git"
product.json products → 0 → price 89.99
university.json university → location → city "Riverside"
university.json university → departments → 0 → courses → 1 "CS 179K"

A separate missing-key test verifies that lookup failure returns an empty result rather than an unrelated value.

FIND Tests

FIND has 17 parameterized execution cases. These tests were designed to verify not only whether paths exist, but also the semantics of nested groups and sibling targets.

Nested Paths

FIND {"employees" {"0" {"name"}}}

Expected result: true

Siblings Are Not a Path

FIND {"employees" "0" "name"}

Expected result: false

Same-Level Siblings

FIND {"employees" "company_info"}

Both root keys exist, so the result is true.

Missing Sibling

FIND {"employees" "budget"}

One requested sibling is missing, so the result is false.

Out-of-Range Index

FIND {"employees" {"10" {"name"}}}

An array index beyond the available values returns false.

Special Values

FIND is also tested with empty keys, Unicode keys, empty structures, and keys whose value is null.

These cases directly test one of the most important query-language rules: a nested group descends from the component immediately preceding it, while siblings remain at the current JSON level.

DISPLAY Tests

DISPLAY has 11 parameterized execution cases covering successful retrieval and failure behavior.

Nested Value

DISPLAY {"employees" {"0" {"name"}}}

Expected: "Laura"

Array Index

DISPLAY {"employees" {"0" {"skills" {"1"}}}}

Expected: "Git"

Multiple Leaves

DISPLAY {"employees" {"0" {"name" "salary"}}}

Expected: ["Laura", 90000]

Unicode Result

DISPLAY is tested against escaped Unicode keys and Unicode values.

Missing Leaf

DISPLAY {"employees" {"0" {"name" "age"}}}

If one required leaf is missing, the result is empty.

Empty Array

Attempting to DISPLAY element 0 of an empty array returns an empty result.

FILTER Testing

The current query-parser tests verify both FILTER formats.

Regex FILTER Parsing

FILTER {"employees" {"name"}} "^L"

The parser verifies that isRegexFilter is set to true.

Numeric FILTER Parsing

FILTER {"employees" {"salary"}} 80000 100000

The parser verifies that isRegexFilter is false.

Current automated-test gap: the test files in the current project archive do not yet include GoogleTest cases that execute FILTER end-to-end through json_parser::parsejson(). FILTER behavior has been exercised manually, but adding automated regex and numeric FILTER execution cases would strengthen regression coverage.

Unicode and Escaped-Key Tests

Unicode handling receives dedicated fixture coverage because keys and values may use different UTF-8 widths or JSON \uXXXX escapes.

The Unicode parameterized suite contains 14 cases.

Accented Latin

"naïve" → "café"

Cyrillic

"привет" → "мир"

Arabic

"مرحبا" → "العالم"

CJK

"城市" → "東京"

Emoji

"emoji😀" → "🌍"

Surrogate Pairs

Tests verify decoding of a two-escape UTF-16 surrogate pair into a single four-byte UTF-8 character.

Raw vs. Escaped Forms

Tests also verify that equivalent escaped and raw representations can match: 

\u00e9  ↔  é

Unpaired Surrogates

Invalid standalone lead and trail surrogates are expected to remain as literal escaped text rather than being incorrectly converted.

File Handling Tests

File behavior is tested separately from query execution.

  • Basic fixtures employee.json, product.json, and university.json must open successfully.
  • A missing filename must remain closed and return the expected error state.
  • An empty filename must not open a file.
  • Rechecking an already-open stream must still report success.
  • jsonToString() must copy expected JSON content into a non-empty string.
  • isFileOpen() is checked against both valid and invalid streams.

Why Parameterized Tests Are Used

Many behaviors differ only in their input and expected output. GoogleTest parameterization allows the same assertion logic to run over a table of cases. 

struct FindCase {
    const char* name;
    const char* filename;
    const char* query;
    const char* expected;
};

Each case receives a descriptive name, so failed test output identifies the exact behavior that regressed.

This approach reduces repeated test code while keeping each behavioral case independently visible in GoogleTest and CTest.

Test Design

Behavior-Oriented Names

Cases use names such as SiblingsAreNotAPath and RejectsIndexPastEndOfArray so the intended rule is clear from the test report.

Positive and Negative Cases

Tests verify both successful lookups and expected failures.

Real JSON Fixtures

Traversal tests use actual JSON documents rather than only synthetic strings embedded inside the test source.

Exact Output Comparison

Returned JSON text is compared against exact expected values whenever possible.

Regression Coverage

Edge cases such as Unicode escapes, empty keys, embedded null bytes, and missing paths protect previously fragile behavior.

Independent Fixtures

Basic, Unicode, and edge-case data are separated into dedicated files to make failures easier to isolate.

Test Fixture Map

Current Testing Gaps

Coverage to Add

  • End-to-end regex FILTER tests

  • FILTER with no matching values
  • Malformed FILTER arguments
  • More CLI-level integration tests
  • Performance regression tests

After running ./build/JSONQL or ctest --output-on-failure, update this section with the final number of passing and failing tests from that run.

A final version could report: 

Automated tests: 96 total
Passed: [update after final run]
