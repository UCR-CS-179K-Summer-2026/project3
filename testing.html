Testing Strategy

The project uses GoogleTest for correctness testing and a separate benchmark executable for performance experiments. Parameterized tests are used when several inputs should follow the same behavior.

Area What Is Verified Why It Matters
File handling Valid fixtures open correctly, invalid filenames fail, and files can be converted into strings. Confirms JSON processing begins from a valid input.
JSON traversal Object keys, array indices, nested values, numbers, strings, and missing paths. Exercises the core lookup behavior.
FIND Nested paths, siblings, missing values, array bounds, Unicode keys, and empty structures. Verifies existence-check semantics.
DISPLAY Nested values, array values, sibling leaves, Unicode output, and missing paths. Confirms selected JSON values are returned correctly.
FILTER Regex and numeric filters, full and partial result sets, selected fields, and no-match behavior. Verifies FILTER execution as well as parser classification.
JSONL Per-record queries, zero-based record indexing, nested lookups, FIND aggregation, and missing/out-of-range cases. Confirms newline-delimited JSON is handled independently record by record.
Unicode & edge cases Unicode escapes, emoji, surrogate pairs, null, booleans, empty structures, embedded null bytes, and unusual keys. Protects behavior outside simple JSON examples.
Query parsing Nested groups, quoting, whitespace, malformed syntax, parser state, and FILTER classification. Verifies correct construction of ParsedQuery.

Representative Test Pattern

Many traversal checks use one parameterized test with different fixture, path, and expected-value cases. This avoids repeating the same setup for every input. 

TEST_P(JsonBasicParseTest, ReturnsExpectedValue) {
    const auto& test = GetParam();

    std::ifstream file(test.filename);
    ASSERT_TRUE(file.is_open());

    const std::string jsonText =
        json_parser::jsonToString(file);

    const std::string result =
        json_parser::parsejson(jsonText, test.path);

    EXPECT_EQ(result, test.expected);
}

Each parameterized case receives a descriptive name, making regressions easier to identify in the test output.

Running the Test Suite

Configure and build the project from the repository root: 

cmake -S . -B build
cmake --build build

Run the GoogleTest executable directly: 

./build/JSONQL

Or run the registered tests through CTest: 

cd build
ctest --output-on-failure

Query Parser Tests

Query parser tests verify that raw query text becomes the expected recursive ParsedQuery structure.

Simple Queries

FIND {employees}

Tests basic command and field parsing.

Nested Queries

FIND {employees {0 {name}}}

Verifies recursive brace groups.

Quoted Keys

FIND {"first name"}

Spaces inside quotation marks remain part of the key.

Whitespace

FIND   {employees    name}

Repeated spaces do not create empty tokens.

Malformed Input

Invalid commands, unmatched braces, and unterminated quoted strings are rejected.

Parser State

Consecutive queries replace previous parser state and FILTER metadata is reset correctly.

Basic JSON Traversal Tests

Small fixture files are used to verify representative paths through objects and arrays.

Fixture Path Expected Result
employee.json employees → 0 → name "Laura"
employee.json employees → 2 → salary 95000
employee.json employees → 0 → skills → 1 "Git"
product.json products → 0 → price 89.99
university.json university → location → city "Riverside"

Missing-key behavior is also tested to confirm that invalid paths return an empty result.

FIND Tests

The suite contains 17 FIND cases covering both successful lookup and expected failure.

Nested Path

FIND {"employees" {"0" {"name"}}}

Expected: true

Siblings Are Not a Path

FIND {"employees" "0" "name"}

Expected: false

Same-Level Siblings

FIND {"employees" "company_info"}

Both root-level fields exist.

Failure Cases

Tests cover missing siblings, out-of-range indices, empty arrays, and empty objects.

Special Keys

Empty keys and Unicode keys are tested explicitly.

Null-Valued Keys

A key whose value is null still counts as existing.

These cases verify the distinction between sibling query components and nested descent.

DISPLAY Tests

The suite contains 11 DISPLAY cases covering retrieval of nested and sibling values.

Nested Value

DISPLAY {"employees" {"0" {"name"}}}

Returns the requested employee name.

Array Value

DISPLAY {"employees" {"0" {"skills" {"1"}}}}

Returns: "Git"

Sibling Leaves

DISPLAY {"employees" {"0" {"name" "salary"}}}

Multiple requested values are returned together.

Unicode Output

Unicode values are verified through DISPLAY.

Missing Values

Missing keys and missing leaves return an empty result.

Empty Arrays

Invalid lookup into an empty array also returns an empty result.

FILTER Tests

FILTER is covered at both the query-parser and execution levels. The latest suite includes eight end-to-end FILTER cases in addition to parser tests that distinguish regex and numeric-range syntax.

Regex FILTER

FILTER {"employees" {"name"}} "^L"

Parser classification is tested, and execution tests verify regex-based filtering against fixture data.

Numeric FILTER

FILTER {"employees" {"salary"}} 80000 100000

Parser classification is tested, and execution tests verify numeric-range filtering and selected-field output.

Current coverage: FILTER execution now includes employee and product fixtures, full and partial result sets, regex matching, numeric filtering, selected fields, and no-match behavior.

Unicode and Edge-Case Tests

The test suite includes dedicated cases for values that are easy to mishandle during direct JSON scanning.

Unicode

Accented Latin, Cyrillic, Arabic, Greek, CJK, and emoji keys are tested.

Unicode Escapes

\u00e9  ↔  é

Escaped and raw Unicode representations are compared.

Surrogate Pairs

Valid pairs are decoded while unpaired surrogates remain safely represented.

Primitive Literals

null, booleans, negative numbers, decimals, and exponent notation are verified.

Embedded Nulls

Escaped and raw embedded null bytes are tested to ensure traversal does not truncate unexpectedly.

Empty Structures

Empty arrays, empty objects, and the legal empty key "" are tested explicitly.

Sample and Stress-Test Data

The repository separates fixtures by purpose:

  • jsonFiles/basic/ — employee, product, and university traversal examples.
  • jsonFiles/edgecases/ — null values, embedded nulls, literal types, and empty structures.
  • jsonFiles/unicode/ — Unicode keys, escaped quotes, unusual keys, and surrogate cases.
  • jsonFiles/jsonl/ — newline-delimited JSON fixtures used for per-record queries, indexing, nested lookups, and FIND behavior.
  • Bookings_1-level_1-KB_formatted.json and Bookings_1-level_1-MB_formatted.json — benchmark inputs.
  • big.json — larger nested data used for broader traversal and performance experiments.

Test Design

Parameterized Cases

One test body can verify many input/output pairs without duplicating setup code.

Descriptive Names

Cases such as SiblingsAreNotAPath identify the exact rule being checked.

Positive and Negative Cases

Successful queries and expected failures are both covered.

Exact Comparisons

Returned JSON values are compared against explicit expected output.
