JSON Query Engine — Architecture, Design, and Algorithms

GitHub repo link: Click Me!

The JSON Query Engine is a C++20 project for querying structured JSON data. The system separates query processing from JSON processing: one subsystem parses and interprets user queries, while the other traverses JSON objects and arrays to retrieve the requested value.

The current repository includes a recursive query parser, a structured ParsedQuery, integrated FIND and DISPLAY execution, a pointer-oriented JSON traversal engine, a command-line interface, automated GoogleTest suites, JSON edge-case fixtures, and performance benchmarks.

System Architecture

At a high level, the system is designed as a pipeline. JSON data and a user query enter through separate paths, then meet at the execution layer. The query side determines what operation should happen; the JSON side provides the data that operation acts on.

Current-state note: the architecture now includes an integrated query-to-JSON path for FIND and DISPLAY. parsejson() coordinates command execution, while findGroup(), displayGroup(), and seekComponent() handle the command-specific and traversal work. FILTER and ALLOF are the main execution paths still under development.

System Design

The design separates responsibilities so that query syntax, command selection, JSON traversal, and low-level JSON scanning can evolve independently. This also makes individual components easier to unit test.

Main Program

main.cpp is the command-line controller. It loads the JSON file, accepts repeated user input, calls queryparser::parsequery(), and passes the resulting parsed query into JSON execution.

Query Parser

The query parser is implemented in include/queryparser.h and src/queryparser.cpp. It converts raw query text into recursive JSONType values so nested groups remain structured. 

struct JSONType {
std::variant<
    std::string,
    std::vector<JSONType>
> structure;
};

For example, FIND {a b {c d {e f}}} preserves the nested groups instead of flattening them into a single list.

Parsed Query

The parser stores the completed query in a ParsedQuery structure. This keeps the recursive query parts together with the requested command and FILTER metadata. 

struct ParsedQuery {
std::vector<JSONType> parts;
Query command;
bool isRegexFilter = false;
};

Query Reader

QueryReader and QueryConstruct remain part of the repository and document an earlier interpretation-oriented design. The current MVP path uses ParsedQuery directly for JSON execution, so they are not the primary path shown in the current execution diagrams.

JSON Processing

The JSON processing layer is implemented in include/jsonparser.h and src/jsonparser.cpp. parsejson() coordinates the requested operation. FIND delegates to findGroup(), DISPLAY delegates to displayGroup(), and both rely on seekComponent() to locate individual object keys or array indices.

Lower-level helpers such as skipWs(), scanStringSpan(), skipValue(), toIndex(), and convertUnicode() support traversal without building a complete in-memory JSON object tree.

Core Data Structures

JSONType

Represents recursive query syntax. A value can hold either a string token or another vector of JSONType values.

Why it matters: nested braces can be preserved instead of flattened.

ParsedQuery

Represents the completed parser output. It stores the recursive query parts, the selected command, and FILTER metadata.

Why it matters: JSON execution receives information the parser already knows instead of inferring it again.

Module Interfaces

Execute a Parsed Query

Executes the parsed query against the JSON document. The execution layer then uses findGroup(), displayGroup(), and seekComponent() as needed.

Algorithms

1. Query Parsing Algorithm

The query parser scans the input one character at a time and preserves nested groups using recursive JSONType values.

  1. Collect normal characters into the current token.
  2. Use whitespace to separate tokens.
  3. Handle quoted tokens without splitting their contents.
  4. When an opening brace is found, begin a nested group.
  5. Parse the contents of the group recursively.
  6. Return to the previous level when the matching closing brace is found.
  7. Store the final result in ParsedQuery.

2. FILTER Identification Algorithm

FILTER type is identified from the parsed query structure. One argument after the path represents a regular-expression FILTER, while two arguments represent a numeric range. This decision is stored in ParsedQuery.isRegexFilter.

Regex FILTER

FILTER {"employees" "name"} "^L"

One argument follows the path.

Numeric FILTER

FILTER {"employees" "salary"} 80000 100000

Two arguments follow the path.

3. parsejson() — Query Execution

parsejson() is the high-level execution entry point. It receives the JSON document together with the parsed query, checks the requested command, and delegates the operation to command-specific logic.

  • FIND delegates to findGroup().
  • DISPLAY delegates to displayGroup().
  • FILTER and ALLOF remain the main command paths still being completed.

4. seekComponent() — JSON Traversal

seekComponent() locates one requested component from the current JSON location. If the current value is an object, the component is treated as a key. If it is an array, the component is converted to an index. Unmatched values are skipped using skipValue().

Object Lookup

  1. Scan the next object key.
  2. Compare it with the requested component.
  3. Skip nonmatching values.
  4. Stop when the requested key is found.

Array Lookup

  1. Convert the component to an array index.
  2. Walk through array elements.
  3. Skip elements before the requested index.
  4. Stop at the selected element.

5. findGroup() — FIND Algorithm

findGroup() verifies that all requested items in a FIND group exist. String items use seekComponent(); nested groups call findGroup() recursively.

6. displayGroup() — DISPLAY Algorithm

displayGroup() follows the requested group structure and collects the JSON values that should be returned. A key may either be used as navigation into a nested group or be added directly to the output results.

7. skipValue() — Value Skipping Algorithm

A major helper operation is skipping JSON values that are unrelated to the current lookup. Strings are skipped as complete quoted spans, objects and arrays use nesting depth, and other values advance until a JSON delimiter is reached.

8. Unicode and Escape Handling

The JSON parser includes support for escaped strings, Unicode escape sequences, UTF-8 keys, and surrogate-pair cases. convertUnicode() converts supported Unicode escapes so keys and returned values can be handled consistently.

Design Decisions & Optimizations

Direct JSON Scanning

The parser scans the original JSON text instead of building a complete in-memory JSON object tree. This reduces object allocation and allows the engine to ignore data that is unrelated to the requested path.

Skip Irrelevant Values

During object and array traversal, unmatched values are skipped rather than fully parsed. The search can also stop once the requested value has been located.

std::string_view During Scanning

The parser accepts the JSON input as std::string_view, which allows it to inspect the existing string buffer without first duplicating the entire document.

Recursive Query Representation

JSONType preserves nested query groups directly. This keeps syntactic structure available to later stages instead of flattening the query and then attempting to reconstruct it.

Unicode and Escape Handling

The JSON parser includes handling for escaped strings, Unicode escape sequences, UTF-8 keys, and surrogate-pair cases. These behaviors are important because object-key comparison must work even when the JSON encodes text differently from the user-facing key.

Testing Strategy

The project uses GoogleTest for correctness testing and a separate benchmark executable for timing experiments. Parameterized tests are used when several inputs should satisfy the same behavior, which keeps the assertions consistent while still giving each case a descriptive name.

Area What is verified Why it matters
File handling Basic fixtures open, missing/empty filenames fail, repeated open checks remain valid, and files convert to strings. Confirms the parser starts from a reliable input source.
Basic JSON traversal Object keys, array indices, nested objects, nested arrays, strings, integers, decimals, and missing keys. Exercises the main lookup algorithm on representative paths.
Escapes & Unicode Escaped quotes, unusual keys, raw UTF-8, Unicode escapes, and surrogate-related cases. Checks that key comparison works across JSON string encodings.
Literal & edge values null, booleans, negative numbers, exponent notation, escaped null sequences, embedded raw null bytes, empty arrays, and empty objects. Protects against parser failures outside simple textbook JSON.
Query parsing Simple and multi-field queries, array-index tokens, nested/deep groups, repeated whitespace, quoted tokens, empty input, malformed braces, and replacement of prior parser state. Verifies recursive syntax construction and parser state management.

Representative Test Pattern

Many traversal checks use one parameterized test with different fixture/path/expected-value cases. This makes it easy to add coverage without duplicating the same setup and assertion logic. 

TEST_P(JsonBasicParseTest, ReturnsExpectedValue) {
const auto& test = GetParam();
std::ifstream file(test.filename);
ASSERT_TRUE(file.is_open());

const std::string jsonText = json_parser::jsonToString(file);
const std::string result = json_parser::parsejson(jsonText, test.path);

EXPECT_EQ(result, test.expected);
}

Performance Benchmarks

benchmark.cpp is separate from the correctness suite. It can compare lookup timing on approximately 1 KB and 1 MB booking datasets, and it also measures a spread of paths through big.json, including early/late object keys, missing keys, Unicode/escaped keys, deep paths, array indexing, long escaped values, and a value near the end of the document.

Testing gap to address next: the repository already has strong query-parser and JSON-traversal coverage. The next priority is broader end-to-end coverage for the integrated FIND and DISPLAY paths, followed by FILTER and ALLOF command tests as those execution paths are completed.

Sample and Stress-Test Data

The repository includes several groups of JSON fixtures:

  • jsonFiles/basic/ — employee, product, and university examples
  • jsonFiles/edgecases/ — embedded nulls, literal types, and empty structures
  • jsonFiles/unicode/ — escaped quotes, unusual keys, and Unicode cases
  • Bookings_1-level_1-KB_formatted.json and Bookings_1-level_1-MB_formatted.json — benchmark inputs
  • big.json — broader traversal and performance stress cases

Together, these files exercise shallow and deeply nested structures, objects, arrays, strings, numeric literals, booleans, null, Unicode text, escaped content, missing values, and larger documents.
