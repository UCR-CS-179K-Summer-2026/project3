Performance

The benchmark executable measures JSON lookup performance across small files, larger inputs, controlled traversal cases, and a memory-mapped 1 GB large-file path. The project also records optimization experiments that were tested but not retained.

View Results Benchmark Design

Benchmark Design

Performance experiments are implemented separately from the correctness tests in benchmark.cpp. The executable currently exposes four benchmark modes.

Mode Purpose Status
Single Query Compare lookup time between the small and larger booking datasets. Implemented
Many Queries Intended for repeated multi-query experiments. Not implemented yet
Big File Compare several traversal patterns through big.json. Implemented
Huge File Exercise the memory-mapped parsing path on a locally generated 1 GB JSON document and report query parsing, mapping, and execution timing. Implemented / locally measured
Correctness testing and performance measurement are intentionally separate. GoogleTest verifies that results are correct, while the benchmark executable measures execution time.

Running the Benchmark

Configure and build the project: 

cmake -S . -B build
cmake --build build

Run the benchmark executable: 

./build/benchmark

The program then displays:

Measured Results

Recorded results include a 100-run input-size comparison, a 100-run controlled traversal benchmark, and a 100-run 1 GB memory-mapped query benchmark.

Input-Size Comparison

The Single Query benchmark was repeated 100 times. The reported result is the average elapsed time for each file and lookup.

Dataset Lookup Average Time
~1 KB booking file Entry 0 → Booking_ID 0.0348 ms
~1 MB booking file Entry 1800 → Booking_ID 0.9704 ms 
average of 100 runs
1 KB, entry 0:      0.0348179 ms
1 MB, entry 1800:   0.970444 ms

The larger test takes substantially longer because it processes a much larger mapped file and accesses an element farther into the JSON array.

This benchmark includes memory mapping, query parsing, and JSON traversal inside the timed region. It therefore represents an end-to-end lookup rather than pure traversal time. The current implementation uses mapFile() for both booking datasets; it no longer copies either file into a separate std::string first.

Interpreting the Results

Input Size Has a Visible Effect

The end-to-end booking benchmark increased from about 0.0348 ms on the small input to about 0.970 ms on the larger input.

Traversal Is Lightweight on Small Fixtures

The controlled big.json queries complete in roughly 9.5–28.3 microseconds on this benchmark run.

Unicode Handling Remains Comparable

Raw UTF-8, escaped Unicode, surrogate-pair, and escaped quote lookups remain within the same general timing range.

Query Shape Matters

Object width, nesting, array navigation, escaping, and target position all change the amount and type of work performed by the traversal helpers.

Sequential Lookup Behavior

The engine does not construct a hash table or global index of all JSON keys. When seekComponent() searches an object, members are examined sequentially until the requested component is found or the object ends.

Therefore, the amount of JSON text that must be examined can depend on where a key appears within its container.

The current microbenchmark does not show a simple “first key is always faster than last key” relationship. At microsecond scale, caching, measurement overhead, branch behavior, and the exact fixture layout can affect individual measurements.

Large-File Optimization: Memory Mapping

The project also includes an alternative loading path for very large files: 

std::string_view json =
    json_parser::mapFile(path);

mapFile() uses a read-only memory mapping and exposes the mapped bytes through std::string_view.

Earlier String-Based Loading

std::ifstream file(...);

std::string json =
    json_parser::jsonToString(file);

This path remains useful for some controlled fixtures, such as big.json, but it creates a complete string copy before querying.

Mapped Loading

std::string_view json =
    json_parser::mapFile(path);

The parser views the mapped file directly without first copying the complete file into another large string.

The main CLI and the Single Query benchmark now use this mapped loading path. It is especially relevant for large JSON files because the traversal functions already operate on std::string_view.

Memory mapping changes how the document is loaded and exposed to the parser. It does not replace the engine's sequential component-search algorithm.

Performance Development History

Earlier benchmark logs are useful for showing how the large-file implementation changed over the course of development. These measurements are not all directly comparable because the loading and timing strategy changed, but they document the progression from copying the JSON into a string toward querying a memory-mapped file.

String-conversion version 4450.31 ms total; 3781.95 ms converting JSON to string The conversion step dominated the total runtime and motivated avoiding a complete file copy.
Initial mmap version 2126.61 ms / 0.505 GB/s Introduced memory-mapped input and removed the full JSON-to-string conversion.
Later mmap benchmark 615.063 ms / 1.746 GB/s Repeated testing showed substantially lower query time after the mmap-based path matured.

Why keep these older results? They demonstrate the engineering progression. The biggest practical improvement was not a micro-optimization inside the parser, but eliminating expensive whole-file copying and operating directly on mapped input.

Attempted SIMD Optimization

One optimization experiment tried to skip uninteresting text in 16-byte chunks. For each chunk, SIMD-style bitmasks were computed for the structural characters ", \, {, }, [, and ].

If every mask was zero, the parser could advance past all 16 bytes because the chunk contained no structural character that required parsing. If any mask was nonzero, execution fell back to the existing character-by-character parser for that region.

Expected Benefit

Long blocks of ordinary text could theoretically allow the parser to skip close to 16 bytes of irrelevant content at once instead of examining each byte individually.

Measured Result

On the project's benchmark data, the SIMD experiment was approximately 2× slower than the existing implementation, so it was not retained.

The likely reason is workload shape. Most keys and values in the tested JSON files were shorter than 16 bytes, so many chunks still contained a quote, escape, brace, or bracket. That meant the code paid for several mask operations and then frequently fell back to the original parsing method anyway.

Large text blocks with few structural characters could benefit much more from this approach in theory, potentially approaching a 16-byte-at-a-time skip in ideal regions. Those regions were not representative of the JSON datasets used by this project, and long free-text blocks are not the common case for the tested workload.

Performance Takeaways

Larger Inputs Cost More

The measured end-to-end lookup increased substantially between the small booking fixture and the approximately 1 MB fixture.

Traversal Can Be Isolated

Loading big.json before timing makes it possible to measure traversal separately from disk input.

Different Paths Exercise Different Work

Nesting, array lookup, Unicode conversion, escaped strings, and missing components all exercise different helper paths.

Memory Mapping Supports Large Inputs

The mapped-file path allows a large document to be exposed as a std::string_view without creating another full-size JSON string.

Optimization Must Match the Workload

The 16-byte SIMD skipping experiment was about 2× slower on the tested JSON because structural characters appeared often enough to trigger frequent fallback to the original parser.
