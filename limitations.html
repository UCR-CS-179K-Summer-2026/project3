Limitations

The current JSON Query Engine supports FIND, DISPLAY, and FILTER, but several parts of the implementation can still be expanded or improved.

Current Limitations

Sequential Lookup

Object keys and array elements are searched sequentially. The engine does not build a persistent index of the document.

Limited Query Language

The current language focuses on FIND, DISPLAY, and FILTER. Aggregation, wildcard navigation, and data modification are not implemented.

FILTER Scope

FILTER supports numeric ranges and regular expressions, but does not currently support complex multi-condition expressions.

JSONL Record Model

JSONL files are processed as independent nonblank records. Queries can scan all records or select one by zero-based index, but there is no cross-record join, aggregation, or persistent index.

Platform-Specific Large Files

The memory-mapped large-file path uses POSIX mmap(), so it may require changes for non-Unix platforms.

Testing and Performance Gaps

Testing

FIND, DISPLAY, FILTER, JSONL traversal, Unicode handling, and malformed-query behavior all have automated coverage. Remaining gaps are mainly broader edge cases, malformed FILTER arguments, CLI integration, and large-file regression tests.

Performance

More controlled benchmarks between approximately 20 MB and 200 MB would provide a stronger scaling and optimization comparison.

Attempted SIMD Optimization

Structural Character Scanning

A SIMD optimization was tested to speed up scanning for JSON structural characters. For each 16-byte block, the implementation generated bitmasks for characters such as ", \, {, }, [, and ]. If no structural character was found, the parser could skip the entire 16-byte block at once. If a structural character was found, parsing fell back to the existing character-by-character method.

In benchmarks, this approach was approximately 2× slower than the existing implementation. Most keys and values in the tested JSON files were shorter than 16 bytes, so the mask usually found at least one relevant character. That meant the SIMD work was often performed only to fall back to the original parser immediately afterward.

The technique could theoretically provide much larger gains for long runs of text with no structural characters—potentially approaching a 16-byte-at-a-time speedup—but that pattern was not common in the project datasets and is not typical of the JSON workloads tested here. Because it reduced performance on representative inputs, the SIMD approach was not kept in the final parser.

Future Improvements

  • Add more malformed and mixed-type FILTER edge-case tests.
  • Add larger and malformed JSONL test cases.
  • Add CLI integration tests, including output-to-file behavior.
  • Improve query error messages and diagnostics.
  • Add more controlled large-file and performance-regression benchmarks.
  • Explore caching or indexing for repeated queries.
  • Make memory-mapped file loading more portable across platforms.
  • Expand the query language with additional operators and multi-condition filters.
The current project is designed as a focused JSON query engine, rather than a complete JSON database or general-purpose query language.
